# GUI 오케스트레이터(Orca) 실험: 실행 층을 바꿔도 판정은 그대로인가

> **상태: AI 초안 · 사람 검토 전.** 리드 역할의 AI(Claude)가 판정 문서와 실행 기록을 바탕으로 썼다. 사람 검토를 마치면 이 표시를 바꾼다.

2026-10-18, 하네스 `core-v0.4.2` → `core-v0.5` 개발 기간.

## 질문

여러 에이전트(구현 · 검토 · 리드)를 오가며 일하다 보니 “어느 세션이었더라”를 찾는 시간이 커졌다. GUI 오케스트레이터는 세션 관리 · 재개 · 검색을 준다. 그렇다면:

1. 실행 경로를 오케스트레이터로 바꿔도 하네스 판정과 결과 품질은 그대로인가?
2. 기존 방식(헤드리스 위임 스크립트)보다 시간 · 토큰에서 나은가?
3. 오케스트레이터의 기본 기능 중 하네스가 의존해도 되는 것은 무엇인가?

## 설정

| 항목 | 값 |
|:---|:---|
| 구현자 | Gemini 계열 CLI 에이전트(편집만 허용, 명령 실행 거부), 두 경로 모두 같은 모델 · 권한 |
| A (기준) | 헤드리스 위임 스크립트: 격리 작업 공간, 자동 타임아웃, 결과 · 사용량 기록 |
| B (후보) | Orca 터미널 에이전트 실행 + 지시 전달 |
| 작업 | 이 하네스의 실제 미해결 항목 — 여러 줄 `raise` 등가 규칙, 단일 인자 끝 쉼표 · 미사용 상수 정리, `builtins` 별칭 금지 호출 |
| 판정 | 같은 판정 사례를 먼저 쓰고, 판정자가 결과 파일만 새 클론에 넣어 직접 실행 + diff 읽기 |
| 측정 | 에이전트 자체 기록(단계별 시각 · 토큰)을 두 경로 공통 출처로 사용, 요청당 상한 10분 |

## 결과 (사실)

| 쌍 | A | B |
|:---|:---|:---|
| 여러 줄 raise (시간은 리드 관측 — 이 쌍만 측정 범위가 달라 비교하지 않는다) | 1회 통과, 8분23초 | 1회차 10분 상한에서 중단 → 피드백 후 2회차 1분09초에 통과 |
| 끝 쉼표 · 정리 | 1회 통과, 모델 활동 3분05초, 입력+출력 12.3만 토큰 | 1회 통과(A 와 **같은 diff**), 2분52초, 12.2만 |
| builtins 별칭 | 1회 통과, 6분22초, 18.3만 | 1회 통과, 5분07초, 16.7만 |

- 세 쌍 모두 품질(판정 사례 통과 · 기존 자기 검사 불변 · 허용 경로만 변경)이 같았다. 경로 오버헤드도 13~16초로 비슷했다.
- 오케스트레이터 기본 기능 시험: **작업 공간 생성 + 에이전트 실행 + 지시 전달을 한 명령으로**, **공식 중지(프로세스 종료 · 실패 표시)** 는 동작했다. **실행 시간 상한은 기본 기능으로 없었다** — 대기 명령의 타임아웃은 “기다림”의 상한일 뿐이었다.
- 감독 모드(질문 · 답변 · 완료 보고)는 명령을 실행할 수 있는 작업자에서만 끝까지 돌았다. 편집 전용 작업자는 완료 보고 명령이 거부되어, 일을 끝냈는데도 오케스트레이터에는 “진행 중”으로 남았다.

## 예상하지 못한 발견 (사실)

1. **기본 실행 인자가 샌드박스를 껐다.** 오케스트레이터 설정에 에이전트별 기본 인자가 있었고, 명령 가능 작업자에게 “승인 · 샌드박스 우회”가 붙어 있었다. 이전에 다른 리드 구성에서 편하게 쓰던 설정이 남아, 새 리드 구성의 권한 가정을 조용히 깼다. 사용량 기록을 만들려고 에이전트 로그 형식을 보다가 로그에 남은 실행 조건(`danger-full-access`)으로 발견했다. 해당 실행의 변경은 허용 범위 안이었지만, 격리는 지시문에만 의존하고 있었다.
2. **감독 모드의 지시문이 편집 전용 권한과 충돌했다.** 오케스트레이터가 앞에 붙이는 지시는 작업자에게 상태 보고 명령을 실행하라고 한다. 편집 전용 작업자는 이를 시도하다 모두 거부되었다(권한 경계는 유지).
3. **리드의 감시 방식이 빈틈이 됐다.** 질문 · 완료 메시지만 기다리다, 작업자가 시작 단계(CLI 업데이트 안내 화면)에서 실패한 표시를 20분 동안 놓쳤다. 메시지와 함께 “조치 필요” 표시도 봐야 했다.

## 해석 (판단)

- 질문 1: **그렇다.** 판정이 실행 경로가 아니라 작업 공간 diff 와 에이전트 기록에만 의존하도록 설계했기 때문에, 실행 층을 바꿔도 판정은 바뀌지 않았다.
- 질문 2: **판단할 수 없다.** 표본 3쌍, 차이는 작았고 단일 실행 편차(B 1회차의 긴 추론) 수준이었다.
- 질문 3: 작업 공간 생성 · 공식 중지 · 세션 재개 · 질문 흐름은 쓸 만했다. **시간 상한과 권한 보장은 오케스트레이터에 맡기지 않는다.**

그래서 “전면 이관”이 아니라 **역할별 제한 도입**으로 정했다: 편집 전용 구현자는 작업 공간 생성 + 실행만, 명령 가능 작업자는 감독 모드, 시간 상한 · 품질 판정 · 병합 통제는 하네스.

## 교훈

- 실행 층은 바꿀 수 있게, 판정 층은 실행 층을 모르게 설계한다.
- 실행 시간 상한은 판정 쪽(또는 자동 타임아웃이 있는 경로)이 쥔다. 사람이 지켜보는 감시는 자동 타임아웃이 아니다.
- 리드나 도구 구성을 바꿀 때마다 에이전트의 **실제** 실행 권한을 점검한다. 설정 파일이 아니라, 실행 기록에 남은 조건으로 다시 확인한다.
- 측정 출처는 경로와 무관한 하나(에이전트 자체 기록)로 통일한다. 경로마다 다른 시계로 잰 시간은 비교할 수 없었다.

## 한계

- 표본이 작고(실제 작업 3쌍), 같은 날 같은 환경 · 같은 모델이다.
- 같은 세션에 이어 보낸 2회차는 대화가 하나로 합쳐져 회차별 시간을 나눌 수 없었다.
- 오케스트레이터 버전 · 설정이 바뀌면 결과가 달라질 수 있다.
