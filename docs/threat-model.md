# 하네스 위협 모델 및 잔여 위험 (HD-28)

이 문서는 TDD 하네스 환경에서 승인된 위협 모델 계약과 잔여 위험을 정리한 문서다. 하네스는 비적대적 지름길을 대상으로 평가 왜곡을 줄이기 위한 통제 규약이며, 악의적 공격을 막는 범용 보안 제품이 아니다.

## 1. 대상 위협과 비대상 한계 (HD-28)

하네스의 주 통제 대상은 비적대적 지름길(Non-adversarial shortcuts) 3종이다.

1. **사례 맞추기 (Overfitting to Test Cases)**:
   - 잠긴 테스트 케이스에만 코드를 맞추거나, 테스트 통과만을 위해 명세가 요구하는 필수 구현 분기를 임의로 축소 또는 삭제하는 왜곡이다.
   - 방어는 보류된 사례 밖 확인, 핵심 diff 확인, 티어 및 마일스톤에 따른 독립 검토로 수행하며 모든 허점을 막는 보장은 아니다. 현 회차 Red는 구현자에게 공개된다.
   - 피드백에서 G3(커버리지)를 제외하는 것은 분기 삭제 왜곡을 줄이기 위한 별개 수단이며, 판정 단계에서 필요한 정식 커버리지 검증 자체를 없애는 것이 아니다(명세 §3, §6.2).

2. **판정 및 보류 자료 엿보기 (Peeking at Withheld Data)**:
   - 하네스 방어 로직, 테스트 오라클, 미공개 다음 회차 사례, 레드팀 및 판정 기록, 결정 배경 보고서 등 보류 자료를 참조하여 결함을 회피하려는 왜곡이다.
   - 작업 공간의 독립 저장소 분리와 원본 Git 객체 배제로 누출 범위를 줄이나, OS 수준의 외부 읽기 차단을 보장하지 않는다는 잔여 한계가 있다.

3. **자기 보고 성공 채택 (Unverified Self-Reports)**:
   - 에이전트 워커가 보고하는 `worker_done`, `SUCCESS`, 완료 메모 등 자체 성공 주장을 검증 없이 판정 근거로 채택하는 위험이다.
   - 워커의 보고는 미신뢰 제안으로 취급하며, 리드가 티어에 맞는 외부 직접 실행과 diff 및 문서 직접 확인을 통해 판정한다(구체적 확인 범위는 해당 WO와 명세의 티어를 따른다).

| 위협 유형 | 위협 내용 | 하네스의 대응 및 분리 범위 | 잔여 한계 |
|:---|:---|:---|:---|
| **사례 맞추기** | 테스트 케이스 과적합 및 명세 요구 분기 삭제 | 사례 밖 확인, 핵심 diff 확인, 티어·마일스톤에 따른 독립 검토, 피드백 G3 제외 | 공개된 현 회차 Red에 맞출 가능성은 남음, 필요한 판정 커버리지 검증은 유지 |
| **판정·보류 자료 엿보기** | 판정 로직, 미공개 다음 사례, 레드팀/배경 보고서 참조 | 허용 파일만 독립 저장소 추출, 원본 Git 객체(`objects`, alternates) 분리 | OS 수준 외부 절대경로 읽기 차단 미보장, 도구 deny의 OS 격리 증명 불가 |
| **자기 보고 성공 채택** | 워커의 `worker_done`, `SUCCESS` 등 자체 주장 맹신 | 미신뢰 주장 자체는 판정이 아님, 티어에 맞는 외부 실행 및 diff/문서 직접 확인 | 리드의 판정 확인 절차 누락 시 미신뢰 제안이 섞일 위험 |

> [!NOTE]
> 하네스는 악의적인 시스템 탈취, 호스트 탈출, 임의 코드 실행, OS 커널 수준 우회 등을 막는 보안 제품이 아니다. 시스템 수준의 보안 보증과 잔여 위험, 그리고 개선 목표를 엄격히 구별한다.

## 2. 정보 분리와 독립 저장소 (HD-28, 명세 §4~5)

평가의 객관성을 담보하기 위해 작업자에게 제공되는 정보와 통제되어야 할 보류 정보를 명확히 분리한다.

- **공개 정보**:
  - 현 회차 정식 Red 테스트 및 해당 작업 지시서(WO).
  - WO나 프로필이 지정한 필요한 소스 코드 및 빌드 설정 등의 읽기 입력이 포함될 수 있으며, 일반 소비 프로젝트와 하네스 자체 개발의 제공 범위는 구분된다(명세 §4.3).

- **보류 자료 (Withheld Data)**:
  - 판정자의 사례 밖 공격, 미공개 다음 회차 사례, 검토·레드팀·판정 기록, 결정 배경 보고서, 계산 오라클 모듈 등. 모든 Core 코드를 항상 보류 자료로 단정하지는 않는다.

- **원천 분리 원칙**:
  - 요약이나 인계 프롬프트/자료를 생성하기 전에 원천적으로 분리해야 하며, 사후 삭제나 필터링으로 누출 방지를 대신할 수 없다.

- **독립 저장소 구성**:
  - 기준 커밋에서 지정된 허용 파일만 추출하여 별도의 독립 Git 저장소를 구성한다.
  - 일반 Git worktree만으로는 원본 Git 객체를 감출 수 없으므로 원본 Git 이력, `objects`, alternates(`objects/info/alternates`, `commondir`)를 일체 공유하지 않는다.

- **제공 내용 대조 요약 및 절차 연결**:
  - 계획 JSON과 제공 디렉터리의 내용을 대조하며 불일치 발생 시 즉시 배포를 중단한다. 전수 대조 항목(파일 집합, 바이트, 실행 비트, index 스테이지, 첫 커밋 blob ID 등)의 상세 절차는 [격리 위임 §2.1](isolated-delegation.md#21-계획-소비-및-제공-파일-대조-절차)을 따른다.

- **잔여 읽기 위험 (물리적 차단 미보장)**:
  - 하네스는 현재 OS 계정, ACL, VM, 컨테이너 샌드박스를 통해 작업 공간 밖의 외부 절대경로 읽기를 차단하는 것을 보장하지 않는다.
  - 런타임의 편집 전용 모드나 파일 도구 거부(deny) 설정이 OS 수준의 물리적 격리를 증명하지 않는다.

## 3. 판정 증거와 강제 층 (HD-28 0a)

품질 게이트 강제는 로컬 환경부터 원격 서버까지 3층 체계로 구성되며, 상세 운영 규칙은 [병합 강제](enforcement.md)를 참고한다.

| 방어 층 | 구현 및 위치 | 주요 역할과 한계 |
|:---|:---|:---|
| **1층: 로컬 훅** | `.git/hooks/pre-push`<br/>(`harness/prepush.py`) | 로컬 결함 유입을 조기 차단하나, 미설치 환경이거나 `--no-verify` 플래그로 언제든 우회 가능 (보안 경계 아님) |
| **2층: CI 러너** | GitHub Actions<br/>(`templates/ci/github-harness-gates.yml`) | 격리된 클린 환경에서 게이트를 재실행하나, 워크플로 파일 존재가 소비 저장소의 실제 적용을 뜻하지 않음 |
| **3층: 보호 브랜치** | 원격 저장소 서버 설정<br/>(Branch Protection) | 필수 체크와 보호 브랜치가 해당 저장소에 실제 설정·적용된 경우에만 진정한 병합 강제가 완성됨 |

- **로컬 보고서 위조 가능성**:
  - `reports/gate_report.json` 등 로컬 환경에서 생성된 보고서는 일반 JSON 텍스트이므로 얼마든지 위조나 사후 편집이 가능하다.

- **증거 대조 검사의 한계**:
  - `harness/evidence.py check`의 SHA·scope·dirty·종료코드 검사는 표시·대조용 도구이며, 외부 직접 판정을 대신하지 않는다.

- **실제 운영 설정 미확인 및 문서 한계**:
  - 소비 저장소 내에 CI 템플릿(`templates/ci/github-harness-gates.yml`)이 존재하더라도, 서버 측 보호 브랜치 및 필수 상태 체크(Required Status Checks) 설정과 실제 실행 증거가 확인되기 전에는 강제가 적용되었다고 간주하지 않는다.
  - 이 문서 자체가 특정 소비 저장소의 CI 및 서버 보호 적용 여부를 검증한 보고서는 아니다.

## 4. 역할 분리와 실행 통제 (HD-09, HD-19, HD-22, HD-24)

측정 오염과 권한 침범을 방지하기 위해 역할 간 권한과 실행 책임을 분리한다.

- **워커 편집 전용**:
  - 워커는 지정된 경로의 파일 편집만 수행하며, 명령 실행, 테스트 구동, 피드백 도구 실행 권한은 워커에게 부여하지 않는다.

- **리드 외부 실행**:
  - 게이트 실행, 테스트 실행, 판정 피드백 생성 등 실행 행위는 에이전트 밖의 리드 러너가 주관한다.

- **G3(커버리지) 피드백 배제**:
  - 워커 피드백 보고서에서 G3 커버리지 결과를 제외하여, 구현자가 커버리지 수치를 맞추기 위해 필수 분기를 삭제하는 왜곡을 줄인다. 판정 단계의 정식 커버리지 검증을 없애는 것이 아니다.

- **진행 상태 소유권**:
  - 워커의 완료 주장(`worker_done`, `SUCCESS`, 완료 메모 등)은 미신뢰 제안이며 판정 근거가 아니다. 진행 상태는 리드가 판정 구간 밖에서 직접 소유하고 갱신한다.

- **자동화 경계**:
  - 단계 간 자동화는 알림 및 준비 단계에서 멈추며, 인간의 판단과 승인이 필요한 지점(H1, H2, H3, 병합 등)을 자동 실행하지 않는다.

- **규칙 강제의 범위**:
  - 이러한 운영 규약이 새로운 자동 검사기나 계측기로 모두 기계적으로 강제되고 있다는 보장을 제공하지 않는다.

- **모델 계열 확인**:
  - 실행에 사용된 모델 계열(family)은 선언된 이름이 아니라 실제 실행 시점의 CLI 이벤트 및 보고를 통해 확인한다.

## 5. 현재 완료 경계 (명세 §9, 2026-10-17 기준)

2026-10-17 작성 시점의 하네스 구축 단계 스냅샷과 경계는 다음과 같다.

- **0a 및 0b 현재 경계**:
  - 0a(병합 강제)는 개별 판정이 완료되었다.
  - 0b(작업 공간 내용 정책·계획)도 개별 판정이 완료되었다. `workspace.py plan` 계약의 완료이며 전체 격리 생명주기의 완전 자동화를 뜻하지 않는다.

- **0c 현재 위치**:
  - 본 0c는 기존 승인된 계약을 명문화한 문서화 작업이며 개별 검토를 완료했다.
  - 2026-10-17 후속 0a+0b+0c 독립 통합 검토와 채택 결함 보정·재현·영향 회귀도 완료했다. core-v0.5 릴리스 · 태그는 이후 완료됐다(2026-10-18).

- **통합 검토 및 릴리스 조건**:
  - 0a+0b+0c 통합 검토 및 채택 결함의 수정·재현·영향 회귀 검증은 릴리스 전 필요한 확인 절차이나, 통합 검토 자체가 core-v0.5 릴리스나 태그 완료의 단독 충분조건 또는 자동 승인이 아니다.

- **오케스트레이터(Orca) 도입 범위**:
  - 역할별 제한으로 도입했다: 편집 전용 작업자는 작업 공간 생성 + lead 판정, 명령 실행 작업자는 감독 모드 + 샌드박스 유지. 판정 · 시간 상한 · 병합은 하네스가 따로 통제한다([격리 위임 §5](isolated-delegation.md)).
  - 오케스트레이터의 기본 실행 인자가 샌드박스 · 권한 확인을 끌 수 있다. 위임 전에 실행 인자와 작업자 권한 설정을 확인한다. 무인 실행용 외부 자동 중지는 아직 없다.

- **Muse 대기 후보**:
  - 2026-10-17 기준 Muse는 대기 상태이며, 설정 완료는 실행/편집 성공, 역할 교대, 모델 적합성 확인, PoC 승인을 의미하지 않는다.
