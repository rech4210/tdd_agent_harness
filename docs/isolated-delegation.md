# 격리 위임

구현자가 **작업 지시서와 잠긴 테스트만** 보고 일하게 하는 절차다. 구현자는 하네스의 방어 장치(우회 패턴, 고친 구멍, 회귀 후보, 레드팀 기록, 결정의 배경 보고서)를 모른다. 정보 조건을 고정해야 "하네스가 구현자를 붙잡는가"를 측정할 수 있다. 잠금과 판정은 main에만 있다.

이 절차는 어떤 에이전트 도구에도 의존하지 않는다. 사람이 여는 대화형 세션, 에이전트 CLI의 비대화형 모드, 위임 도구 중 무엇을 써도 된다.

하네스가 다루는 위협 모델과 정보 분리 범위, 잔여 위험 계약은 [위협 모델](threat-model.md)을 참고한다.

## 1. 절차

| # | 단계 | 할 일 | 확인 |
|:---|:---|:---|:---|
| 1 | 기준 확인 | 기준 태그 `<slice>-base` = 테스트 잠금 + 지시서 확정 커밋 | main에서 잠금 검사가 통과 |
| 2 | 꺼낼 목록 | 지시서 §2(읽기 허용) + §3(쓰기 허용) + 빌드 · 실행에 필요한 최소 설정 | 아래 "넣지 않는 것"이 목록에 없다 |
| 3 | 격리 저장소 만들기 | 기준 태그에서 목록만 꺼내 **별도 저장소**를 만들고 첫 커밋 | 첫 커밋 = 구현자 diff의 기준 |
| 4 | 명세 사본 | 구현자가 읽어야 할 외부 문서가 있으면 사본을 격리 저장소 **안에** 둔다 | 위임 도구가 작업 공간 밖 읽기를 거부할 수 있다. 권한 전체 해제로 풀지 않는다 |
| 5 | 위임 | 아무 에이전트 도구로. 입력은 지시서 한 장. 위임 도구가 편집 뒤 지시서 `feedback` 명령을 돌려 결과(`reports/feedback_report.json`)를 에이전트에게 돌려주는 루프(내부 반복 상한 예: 3)를 둘 수 있다. 에이전트에게 명령 권한은 주지 않으며(HD-09), 커버리지(G3)는 피드백에 넣지 않는다(구현자가 분기를 지우는 왜곡 방지). 피드백 게이트 명령은 커버리지를 출력하지 않는다 (파일로만, 그 파일은 피드백 뒤 지운다). 반복 수는 위임 기록에 남기고, 하네스 KPI 는 `config/delegation.toml` 의 `feedback_key` 로 읽는다 | 사람은 지시서 밖의 지시를 하지 않는다 |
| 6 | 회수 | 격리 저장소에서 **쓰기 허용 경로의 diff만** 패치로 만든다 | 그 밖의 변경은 버리고 기록한다 (G0 위반 지표) |
| 7 | 적용 | main에 패치를 적용하고 커밋 | 패치가 쓰기 허용 경로만 건드린다 |
| 8 | 판정 | main에서 게이트 명령 (`python harness/run_gates.py --role implementer --base <slice>-base --slice <slice> --cause implementer|test|harness`). **G3(커버리지) 실패는 테스트 작성자가 먼저** "테스트 빈틈 / 구현자의 쓸모없는 코드"를 판정. **시각 · 난수를 쓰는 슬라이스는 diff 읽기 항목에 "시계 · 난수 · 환경 직접 접근" 고정** (정적 검사 G1 은 이름의 마지막 두 마디만 본다는 한계) | 위임 도구 · 에이전트의 성공 보고는 판정에 쓰지 않는다. 테스트 빈틈이면 테스트 보강 · 재잠금(H3)으로 넘기고 구현자 회차로 세지 않는다 |
| 9 | 수정 루프 | 구현자 원인 실패만, 실패한 게이트 이름과 메시지를 전달. 구현자에게 넘길 때 기본 문구: **"명세가 요구하는 분기는 지우지 말고 보고"** | 방어 장치의 설명을 붙이지 않는다. 테스트 · 하네스 원인은 구현자에게 돌려보내지 않는다 (구현자가 커버리지를 맞추려고 명세 요구 분기를 지우는 왜곡 방지) |

### 넣지 않는 것

| 경로 · 자료 | 이유 |
|:---|:---|
| `harness/`, `adapters/` | 우회 패턴과 판정 로직 |
| 결정 기록의 배경 보고서, 문제 기록, H3 승인 자료, 검토 · 레드팀 보고서 | 고친 구멍과 남은 빈틈이 적혀 있다 |
| 회귀 세트 · 검증 빌드 | 정답 구현이다 |
| 계산 오라클이 든 테스트 지원 모듈 | 구현자가 코드를 그대로 옮겨 오라클과 구현이 같은 맹점을 공유하게 된다 (H-09, 이슈 #30). 오라클은 기대값 표 · 성질이 기본이며, 계산 오라클이 든 모듈은 격리 저장소에 주지 않는다 |
| 다른 슬라이스의 지시서 | 지시서는 슬라이스마다 유일한 계약이다 |
| 잠금 파일 · 판정 보고 | 격리 저장소에서는 잠그지도 판정하지도 않는다 |

## 2. 명령 예 (POSIX 셸)

```sh
BASE=<slice>-base
WORK=../<project>-impl-<slice>          # 프로젝트 작업 트리 밖
PATCH="$WORK.patch"                     # 패치도 작업 트리 밖에 둔다 (G0 가 새 파일로 집계하지 않게)
mkdir -p "$WORK"
git archive "$BASE" -- <읽기 · 쓰기 허용 경로 목록> | tar -x -C "$WORK"
git -C "$WORK" init -q && git -C "$WORK" add -A && git -C "$WORK" commit -qm "base: $BASE"

# ... 위임 (아무 도구) ...

git -C "$WORK" add -A
git -C "$WORK" diff --cached HEAD -- <쓰기 허용 경로 목록> > "$PATCH"
git -C "$WORK" diff --cached --stat HEAD                   # 허용 밖 변경이 있었는지 확인 · 기록
git apply --check "$PATCH" && git apply "$PATCH"           # main 에서
```

Windows PowerShell에서는 `git archive --format=zip -o base.zip $BASE -- <경로>` 후 `Expand-Archive`를 쓴다. 0b 도입 후에는 `harness/workspace.py plan`으로 생성된 계획을 소비하여 독립 저장소를 구성하고 제공 파일을 대조한다.

### 2.1 계획 소비 및 제공 파일 대조 절차

1. **계획 생성**: `python harness/workspace.py plan --base <base> --profile <profile> [--config config/workspace.toml]` 명령으로 제공할 파일 목록(`files`: `path`, `blob`, `mode`)이 담긴 계획 JSON을 얻는다.
2. **독립 저장소 추출 및 구성**:
   - 계획의 `files`에 명시된 파일만 기준 커밋의 blob(`git cat-file blob <blob>`)에서 직접 꺼내 독립 디렉터리에 기록한다.
   - archive 추출을 사용할 경우 `.gitattributes`의 `export-ignore`로 파일이 누락되거나 `export-subst`로 내용이 변환될 수 있으며, 이러한 누락·변환을 포함하여 어떠한 불일치라도 탐지되면 **즉시 배포를 중단**한다. 자동 폴백(대체)하여 작업을 이어나가지 않는다. 리드는 실패 후 별도의 raw-blob 직접 추출을 새로 시도할 수 있으나, 이 경우에도 모든 대조 검증 절차를 처음부터 완전히 다시 수행해야 하며 실패 후의 자동 속행은 허용되지 않는다.
   - 추출 후 독립 디렉터리에서 새 Git 저장소를 초기화(`git init`)하고 첫 커밋을 생성한다. 원본 `.git`, alternates(`objects/info/alternates`), 공유 objects(`commondir`), remote 설정을 일체 이어받지 않아 과거 이력과 보류 blob이 독립 저장소에 남지 않도록 한다.
   - **Git 변환 방지 및 초기 설정**: 워커의 diff 기준 커밋이 왜곡되는 것을 방지하기 위해 새 저장소의 `core.autocrlf`를 `false`로 설정하고(`git config core.autocrlf false`), 내용 변환 필터(smudge/clean, eol 등)를 활성화하지 않는다.
3. **배포 전 대조 검증 (모든 비교 통과 전 배포 금지)**:
   - 파일 집합, 내용 바이트, 실행 비트(mode), archive 누락·변환 등 **어떠한 불일치라도 발생하면 즉시 배포를 중단**하며, 모든 대조 항목이 100% 일치하여 통과하기 전에는 워커에게 어떠한 파일도 전달하지 않는다.
   - `core.autocrlf=false` 설정만으로 내용 일치가 보장된다고 가정해서는 안 된다. `.gitattributes`나 전역 필터 설정 등에 의해 `git add` 과정에서 내용이 변환될 수 있다.
   - 따라서 스테이징 및 첫 커밋 생성 후 다음 항목들을 전수 대조한다:
     - **파일 집합 대조**: 독립 작업 디렉터리의 실제 파일 집합(새 `.git` 내부 제외)이 계획 JSON의 `files` 경로 목록과 정확히 일치하는지 확인.
     - **작업 트리 바이트 대조**: 작업 디렉터리 각 파일의 실제 바이트 내용이 계획의 blob 원문과 완전히 일치하는지 확인.
     - **인덱스 스테이지 대조**: `git ls-files --stage` 결과의 mode뿐만 아니라 **blob ID**까지 계획 항목의 mode 및 blob ID와 일치하는지 대조.
     - **첫 커밋 blob ID 대조**: 생성된 첫 커밋 트리 내 각 파일의 blob ID가 계획의 blob ID와 정확히 일치하는지 확인하여 `git add`/`commit` 과정에서 어떠한 변환도 일어나지 않았음을 증명.
     - **실행 비트(mode) 대조**: POSIX 환경에서는 파일 stat의 실행 비트와 `100755`를 대조하며, Windows 환경에서는 파일 시스템의 POSIX 실행 비트 표현 한계가 있으므로 Git index의 스테이지 모드(`git ls-files --stage`의 `100644` / `100755`)를 계획과 대조.
   - 새 `.git` 자체는 대조 대상에서 제외한다.
   - 이 격리 절차는 작업 공간 내 제공 파일의 조건을 엄격히 제어하는 것이며, OS 권한으로 원본의 절대경로 읽기까지 물리적으로 차단한다고 주장하지 않는다.
4. **실행 계약 시작**: 이렇게 만든 첫 커밋 작업 공간은 `python harness/execution.py manual-start … --workspace-profile <profile> [--workspace-config <설정 경로>]` 로 실행 계약을 시작한다. 하네스가 원본 base 에서 계획을 다시 만들어 워커 저장소(독립 `.git` · alternates 없음 · 부모 없는 단일 커밋 · HEAD 트리 = 계획 · 저장소 객체 = 그 커밋 · 트리 · 계획 blob 뿐)를 확인하고, 점검 단계에서는 제공하지 않은 원본 파일을 새로 만들어 덮어쓰는 변경을 거부한다. 작업 트리 바이트 대조(위 3)는 여전히 리드 몫이다. 프로필 없이 시작하면 지금처럼 워커 HEAD 가 base 와 같아야 한다.

## 3. 함정

| 함정 | 증상 | 대응 |
|:---|:---|:---|
| 위임 도구의 거짓 성공 | 권한 거부로 아무것도 못 했는데 "성공" | 결과는 diff와 게이트로만 판단. 빈 diff = 실패 |
| 작업 공간 밖 읽기 거부 | 비대화형 실행에서 명세를 못 읽고 보고 없이 종료 | 4단계: 사본을 격리 저장소 안에 |
| 대화 이어 가기의 경로 어긋남 | 수정 회차가 **이전 회차의 작업 경로**에 쓰려다 거부됨. 대화 기억 속 코드와 새 작업 공간의 파일이 다름 | 같은 작업 공간을 재사용하거나, 새 회차의 첫 메시지에 작업 경로를 명시. 이전 회차 변경이 새 작업 공간에 들어 있는지 확인 |
| 위임 도구가 프로젝트 작업 트리에 기록을 남김 | 다음 작업자의 G0가 "허용 경로 밖 변경"으로 실패 | 기록 위치를 저장소 밖으로, 또는 `.git/info/exclude`. 프로젝트 설정 파일은 건드리지 않는다 |
| 격리 저장소에서 잠금 · 판정 | 판정의 신뢰가 사라진다 | 잠금 · 판정은 main에만 |
| 하네스 설계자가 구현자 | 방어를 아는 구현 → 측정 오염 | 배정 금지 (`templates/role-assignment-analysis.md`) |
| 위임 도구 실패 회차 | 구현자의 재시도 수가 부풀려진다 | 환경 유형으로 문제 기록, 구현자 KPI에서 제외 |

## 5. 오케스트레이터로 실행 (예: Orca)

오케스트레이터는 **실행 · 세션 층**이다. 판정 · 시간 상한 · 병합은 하네스가 따로 통제한다(판정은 작업 공간 diff · 게이트 · 에이전트 자체 기록만 쓴다).

| 작업자 | 띄우는 방법 | 완료 · 판정 |
|:---|:---|:---|
| 편집 전용 (명령 권한 없음, 예: AGY) | 격리 저장소를 등록하고 작업 공간 + 에이전트 + 지시를 한 번에: `orca repo add --path <격리 저장소>` → `orca worktree create --repo id:<저장소 id> --name <이름> --agent <에이전트> --model <모델> --base-branch <브랜치> --no-parent --prompt "<한 줄>"`. 감독 모드는 쓰지 않는다(감독 지시가 명령 실행을 요구해 편집 전용과 충돌). `--base-branch` 는 지시 파일을 커밋한 커밋으로 주고, 만든 직후 작업 공간에 지시 파일이 있는지 확인한다 | 아래 **감시 도구**를 붙이고, 끝나면 **lead 가 diff · 게이트로 판정** |
| 명령 실행 가능 (예: Codex) | 편집 전용과 같은 방식(`worktree create`). 샌드박스를 유지하면 작업자가 오케스트레이터에 완료를 보고할 수 없으므로(실행 정보 파일을 못 읽음) 감독 모드에 기대지 않는다. 질문 없이 끝까지 가는 지시를 준다 | 감시 도구 + 작업자 세션 로그(완료 · 오류 기록)와 산출물로 끝을 확인, lead 가 판정. Codex 는 지시한 커밋을 하지 않을 수 있다 → lead 가 작업 공간의 `reports/review/*.md` 를 복사해 회수한다. |

**문서 점검 (읽기 전용, HD-52):** 문서 최신화 1단계 점검 Codex 는 Orca 밖에서 실행 환경으로 읽기 전용을 건다 — `python adapters/tools/codex_audit.py --workspace <깨끗한 작업 사본> --prompt-file <지시> --out <작업 사본 밖 결과 파일> [--model gpt-6-luna] [--cap-seconds 900]`. 내부 명령은 `codex exec -s read-only` 고정, 실행 전 작업 사본이 깨끗해야 하고 실행 뒤 바뀌었으면 종료 1, 상한이면 프로세스 트리 전체를 끝내고 종료 3. 결과는 lead 가 `reports/review/` 에 옮기고 편집 목록으로 판정한다. 편집(`doc_editor`) 뒤에는 `run_gates.py --role doc_editor --only G0 --base <점검 기준>` 와 `python adapters/tools/check_handoff_state.py --base <점검 기준>`(`상태:` 줄은 lead 만)를 확인한다.

**감시 도구** (`adapters/tools/orca_watch.py`, upgrade 로 배포): 워커마다 별도 PowerShell 창에서 화면과 작업 공간 변경 파일 수를 간격(기본 60초)마다 보이고, 중간 확인(상한 10분이면 3 · 6 · 10분, 20분이면 5분 간격)을 로그에 한 줄씩 남긴다. 상한이면 lead 세션과 상관없이 작업자에 중단 신호를 보내고 사용량 기록(`model_usage` 의 `cap` · `stop`)을 남긴다. 모델 밖에서 돌아 토큰을 쓰지 않으며, lead 는 로그(`reports/watch/<WO>-<핸들>.log`)만 읽는다.

```powershell
Start-Process powershell -ArgumentList '-NoExit','-NoProfile','-ExecutionPolicy','Bypass','-File','adapters\tools\orca_watch.ps1','--terminal','<handle>','--workspace','<작업 공간>','--agent','agy','--wo','<WO>','--role','implementer','--cap-seconds','600'
```

종료 코드: 0 = 작업자 끝남(유휴 · 터미널 없음, 사용량은 lead 가 `adapters/tools/collect_usage.py` 로 수집), 3 = 상한 중지(기록까지 함), 2 = 인자 오류. 로그에 “중단 신호 실패”가 있으면 lead 가 직접 멈춘다.

| 함정 | 대처 |
|:---|:---|
| 지시(`--prompt`)에 큰따옴표가 든 여러 줄을 넘기면 Windows 에서 인자가 쪼개져 에이전트가 즉시 끝난다 | 지시를 격리 저장소에 파일로 커밋하고, 큰따옴표 없는 한 줄로 “그 파일을 읽고 따르라”고 넘긴다 |
| 편집 전용 작업자에게 테스트 실행을 시킴 | 명령 권한이 없다. “사례를 실행하지 말고 읽어서 맞추라”고 쓴다 |
| 무인 실행 | 오케스트레이터의 대기 체크포인트는 실행 상한이 아니다. 감시 도구가 상한 자동 중지를 맡는다 |
| 지시 파일이 작업 공간에 없음 | 작업 공간이 원격 추적 브랜치에서 만들어지면 로컬로 커밋한 지시가 빠진다. 명령 권한이 없는 작업자는 실패하지 않고 파일을 찾느라 상한까지 시간을 쓴다 → `--base-branch <지시 커밋>` + 만든 직후 확인 |
| 끝난 뒤 | 증거(지시 · transcript · diff)를 보관하고 `orca worktree rm --worktree path:<경로> --force` |
| 감시 창 안 글자를 클릭 · 선택하면 콘솔이 일시 정지(QuickEdit)하고 상한 자동 중지도 멈춘다 | `orca_watch.ps1` 이 자기 콘솔의 QuickEdit 를 끄고 끝날 때 되돌린다(WO-H87). 창이 필요 없으면 `dispatch --no-window` |
| Orca 앱이 꺼지면 작업자도 끝나고 `terminal` 명령이 ‘Orca is not running’ | `orca worktree list` 로 응답 확인, `orca open` 뒤 새 작업 공간으로 다시 위임(잃은 회차도 1칸) |

위임 전에 작업자의 권한 설정(샌드박스 해제 · 권한 생략 인자가 없는지, 편집 전용 작업자의 명령 차단)을 확인한다.
