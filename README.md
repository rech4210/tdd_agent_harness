# tdd-agent-harness

제약으로 코딩 에이전트의 작업을 신뢰할 수 있게 만드는 하네스: **잠긴 테스트 · 세션 밖 게이트 판정 · 역할 분리**.

현재 버전: `core-v0.5.1` · 상태: 실험 단계 · 라이선스: [MIT](LICENSE)

---

## 1. 개요: 무엇이고 어떤 문제를 푸는가

AI 코딩 에이전트에게 단순히 “테스트를 통과시켜라”라고 맡기면, 악의가 없더라도 테스트 코드를 고치거나 테스트에만 끼워 맞추는 게으른 구현 등 다양한 **비적대적 지름길(편법)**을 택하게 됩니다.
**tdd-agent-harness**는 사람의 지속적인 감시에 의존하지 않고, **구조적 제약**을 통해 에이전트가 올바른 TDD(테스트 주도 개발) 규약을 따르도록 강제하는 품질 판정 프레임워크입니다.
사람이 승인한 테스트를 잠그고, 에이전트의 실행 권한을 통제하며, 구현 세션 외부에서 품질 게이트를 독립적으로 판정하여 검증된 코드만 저장소에 병합되도록 만듭니다.

## 2. 동작 흐름 (How It Works)

```text
[사람] 요구사항 정의 및 결정
  │
  ▼
[판정 사례 작성] 실패하는 테스트(Red) 작성
  │
  ▼
[사람] 테스트 승인 및 수정 불가 잠금 (Lock)
  │
  ▼
[구현 에이전트] 편집 전용 격리 작업 공간에서 코드 구현 (명령 실행 권한 없이 설정)
  │
  ▼
[외부 판정자] 에이전트 세션 밖에서 품질 게이트 실행 & diff 직접 검토
  │
  ▼
[독립 레드팀] 다른 모델 계열 AI로 반례 탐색 및 빈틈 검토
  │
  ▼
[사람] 최종 승인, 저장소 병합 및 태그
```

- **판정 사례 (Red)**: TDD의 첫 단계로, 구현 전에 작성하여 의도적으로 실패를 확인하는 테스트 케이스입니다.
- **테스트 잠금 (Lock)**: 사람이 승인한 테스트 코드와 명세를 에이전트가 임의로 수정하거나 우회하지 못하도록 보호 경로로 지정하고 해시를 고정합니다.
- **구현 에이전트 (편집 전용)**: 구현을 맡은 AI는 지정된 파일 편집만 가능하며, 테스트 실행이나 터미널 명령 권한을 갖지 않도록 설정합니다(자기 실행 결과 = 자기 보고).
- **판정자 (세션 외부 실행)**: 에이전트 세션 밖에서 사람이나 리드 러너가 독립적으로 게이트를 직접 실행하고 diff를 검증합니다.
- **계열 분리 & 레드팀**: 구현자와 서로 다른 AI 모델 계열(예: Claude와 Gemini 분리)을 독립 검토자로 배치하여, 구현의 결함이나 반례를 객관적으로 찾아냅니다. 레드팀이 찾은 반례는 명세 계약 안의 실제 피해인지 먼저 선별하여, 타당한 결함만 새 판정 사례로 수용합니다.
- **사람 결정 지점**: 요구사항 결정, 테스트 승인, 최종 병합 등 핵심 책임 구간은 자동화하지 않고 사람이 직접 승인합니다.

> [!IMPORTANT]
> **핵심 원칙: 에이전트의 자기 실행 결과는 자기 보고에 불과합니다.**
> 구현 세션 안에서 에이전트가 출력한 "모든 테스트 통과"라는 자체 주장은 신뢰할 수 없는 제안으로 취급합니다. 오직 구현 세션 밖에서 외부 판정자가 독립적으로 게이트를 실행하고 diff를 직접 검토한 결과만 판정 근거로 인정합니다.

## 3. 빠른 시작 (Quick Start)

```bash
# 1. 새 프로젝트 생성 (하네스 템플릿 복사 및 git 저장소 초기화)
python harness/new_project.py <폴더> --package <이름>

# 2. 품질 게이트 판정 실행 (기준 커밋 대비 구현 결과 검증)
python harness/run_gates.py --role implementer --base <기준 커밋>
```

## 4. 무엇을 막는가: 에이전트의 지름길과 구조적 대응

에이전트가 취하기 쉬운 대표적인 4가지 지름길을 다음과 같은 구조적 장치로 차단합니다:

| 에이전트의 지름길 | 하네스의 구조적 대응 |
|:---|:---|
| **테스트를 고치거나 건너뛰어 통과시키기** | 사람이 승인한 테스트·명세를 잠그고(G0), 건너뛰기·우회 패턴을 차단 |
| **테스트에만 맞춘 게으른 구현** | 분기·함수 커버리지(G3), 돌연변이 점수(G6), 판정자의 사례 밖 확인 |
| **“다 됐습니다”라는 자체 성공 보고** | 판정은 구현 세션 밖에서 판정자가 직접 게이트를 실행한 결과로만 수행 |
| **같은 모델이 스스로 작성하고 검토하기** | 역할 배정 제약(GA): 구현자 ≠ 품질 검토자, AI 모델 계열 분리 |

> [!NOTE]
> 하네스의 주 통제 대상은 비적대적 지름길(사례 맞추기, 보류 자료 엿보기, 검증 없는 자기 보고)이며, 악의적인 시스템 탈취나 호스트 탈출 등 모든 의도적 공격을 막는 범용 보안 제품이 아닙니다. 자세한 통제 범위와 계약은 [위협 모델](docs/threat-model.md)을 참고하십시오.

## 5. 저장소 구조

- `harness/`: 언어 독립적인 판정 엔진과 도구 (게이트 실행, 보호 경로, 요구 추적, 증거 · 병합 강제, 작업 공간 계획, KPI 이벤트)
- `adapters/`: 언어별 도구 연동 (현재 Python: pytest · coverage.py · mutmut · 정적 분석)
- `config/`: 게이트 · 역할 · 아키텍처 · 작업 공간 정책 설정
- `templates/`: 사양 주도 개발(SDD), 테스트 설계, 역할 가이드, CI 틀
- `docs/`: 슬라이스 생명주기, 격리 위임, 병합 강제, 위협 모델
- `case-studies/`: 실제 오케스트레이터 연동 및 운영 사례 연구

## 6. 실행 환경과 오케스트레이터 연동 원칙

하네스는 특정 에이전트 도구나 오케스트레이터에 의존하지 않습니다. 판정에 필요한 것은 **작업 공간의 diff와 에이전트가 남긴 기록**뿐이므로, 동일한 품질 판정을 다른 도구나 실행 환경에 그대로 적용할 수 있습니다.

실제 GUI 오케스트레이터(Orca)를 작업에 붙여 비교·시험하며 정리한 3가지 핵심 원칙:

1. **역할별로 제한하여 사용합니다.**
   - 편집 전용 구현자는 작업 공간 생성과 실행만 맡기고, 작업 완료 여부는 판정자가 diff로 직접 판단합니다.
   - 명령을 실행할 수 있는 작업자만 오케스트레이터의 질문·답변·완료 보고 흐름을 사용합니다.
2. **시간 상한 · 품질 판정 · 병합 통제는 하네스가 직접 관리합니다.**
   - 오케스트레이터의 대기 타임아웃은 '기다림'의 상한일 뿐 프로세스의 실제 실행 시간 상한이 아니었습니다. 사람이 지켜보는 감시 또한 자동 타임아웃을 대체할 수 없습니다.
3. **기본 실행 인자를 점검합니다.**
   - 오케스트레이터 설정에 등록된 기본 인자가 샌드박스나 사용자 승인 절차를 무력화할 수 있습니다. 위임 전에 실제 실행 권한을 점검하고, 에이전트 기록에 남은 실행 조건으로 재확인합니다.

상세한 실험 경위와 비교 데이터는 [사례 연구](case-studies/README.md)에서 확인할 수 있습니다.

## 7. 상세 설계: 검증 티어 및 품질 게이트

### 7.1 검증 강도 티어 및 사람의 결정 지점

코드 변경의 영향도에 따라 검증 강도(Tier)를 3단계로 구분하여 자원을 배분합니다:

| 검증 티어 | 대상 영역 | 필수 검증 절차 |
|:---|:---|:---|
| **T1** | 판정 · 증거 · 권한 · 정보 공개 범위 · 병합 강제 등 핵심 제어 | 판정 사례 작성 + 판정자 직접 실행 + 핵심 diff 전수 검토 + 마일스톤별 독립 레드팀 검증 |
| **T2** | 개발 보조 도구 및 지원 스크립트 | 판정 사례 작성 + 판정자 직접 실행 |
| **T3** | 단순 문서 및 안내 사항 | diff 직접 확인 |

- **사람의 결정 지점 (H1/H2/H3)**:
  - 요구사항 결정(H1/H2), 테스트 승인 및 잠금(H3), 최종 병합은 자동화하지 않고 사람이 직접 판단하고 서명합니다.
- **독립 레드팀 반례 선별**:
  - 레드팀이 찾아낸 반례는 "명세 계약 안의 실제 피해"인지 먼저 선별합니다. 단순 계약 밖의 반례는 예외로 기록하고, 수용된 결함은 다음 회차의 새로운 판정 사례가 됩니다.

### 7.2 품질 게이트 목록

`config/gates.toml` 설정에 기반하여 코드의 품질과 규약 준수를 단계별로 판정합니다.

<details>
<summary><b>품질 게이트 전체 목록 접기/펼치기 (클릭)</b></summary>

| 게이트 ID | 게이트 이름 | 판정 내용 |
|:---|:---|:---|
| **GA** | 역할 배정 제약 | 구현자와 검토자 간 역할 분리 및 상이한 AI 모델 계열 배정 강제 |
| **G0** | 보호 경로 및 잠금 | 사람이 승인한 테스트 잠금, 보호 경로 수정 차단, 우회 패턴 감지 |
| **GT** | 요구 추적성 | 사양 주도 개발(SDD) 문서와 구현 코드·테스트 간의 추적성 검증 |
| **GC** | 헌법 일치성 | "헌법 = 설정" 원칙에 따라 프로젝트 정책과 설정의 일치 여부 확인 |
| **G1** | 아키텍처 적합성 | 레이어 아키텍처 준수, 금지된 import 및 금지된 함수 호출 차단 |
| **G2** | 기능 검증 | 단위 테스트, 성질 기반 테스트, 유스케이스, 가짜 객체(Fake) 계약 검증 |
| **G3** | 커버리지 | 레이어별 분기(Branch) 및 함수(Function) 커버리지 충족 검증 |
| **G4 / G5** | 인수 / 통합 테스트 | 실제 자원 통합 및 인수 테스트 (설정 틀에 예시로 제공되며 기본 비활성화) |
| **G6** | 돌연변이 점수 | 코드 돌연변이(Mutation) 검출 점수 검증 (메시지만 바뀐 예외 등 사람이 정한 등가 규칙 제외) |
| **G7** | 정적 품질 | 코드 복잡도, 정적 타입 검사, 보안 취약점 정적 스캔 |

## 8. 현재 상태와 한계

- **검증 범위**:
  - Python 어댑터 제공
  - 실제 실험 프로젝트 2곳에서 사용
  - `harness/selftest/` 자체 검증 테스트 29개 전수 통과 (공개본 기준)
  - 실험 프로젝트 대상 회귀 검증(판정 동일성) 4/4 통과
- **알려진 한계**:
  - 현재 단일 언어(Python) 어댑터만 지원합니다.
  - 위험도 프로필과 검토 예산은 문서화된 규칙에 기반합니다.
  - 금지 호출 판정(G1)은 함수마다 동일한 별칭 이름을 다른 모듈로 다시 import하는 경우와 동적 속성 접근(`getattr` 등)을 추적하지 못합니다.
  - 로컬 훅은 개발자가 우회할 수 있어, 원격 저장소 서버의 필수 상태 체크가 함께 설정되어야 합니다.

> [!WARNING]
> 로컬 Git 훅은 개발 편의 도구일 뿐 보안 경계가 아닙니다. 완전한 병합 강제를 달성하려면 GitHub 등의 원격 저장소 설정에서 보호 브랜치(Branch Protection)와 필수 상태 체크(Required Status Checks)를 반드시 활성화해야 합니다.
