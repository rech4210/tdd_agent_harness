# 테스트 모듈 머리말 규약

모든 테스트 모듈은 **머리말에 자기가 지키는 ID를 인용한다.** 요구(FR) · 불변식(INV) · 결정(D)에서 테스트로, 테스트에서 요구로 양방향 추적을 하기 위한 규약이다. 지금은 사람이 읽고 grep으로 검사한다. SDD 통합 단계에서 Core의 추적성 게이트(요구마다 테스트 ≥ 1, 테스트마다 요구 ID 인용)가 이 형식을 읽는다.

## 1. 형식

모듈 문서 문자열(Python은 모듈 docstring, 다른 언어는 파일 첫 주석 블록)의 첫 줄은 대상 한 줄 설명, 빈 줄 뒤에 `키: 값` 줄을 둔다.

```
"""<대상>: <무엇을 검사하나 한 줄>.

guards:      FR-012, INV-03, D-21
technique:   01 경계값 표, 02 독립 오라클 성질, 03 경계 근처 생성기
checklist:   B-2, B-3, C-A1, C-A2
decisions:   D-21 (정의역 · 단위), D-22 (해상도: 자르지 않음)
not-covered: <검사하지 않는 것과 이유> (선택)
"""
```

| 키 | 필수 | 값 | 규칙 |
|:---|:---|:---|:---|
| `guards` | **필수** | 쉼표로 구분한 ID. `FR-<3자리>`, `INV-<번호>`, `D-<번호>` | 최소 1개. **`O-xx`는 쓸 수 없다** — 열린 질문을 지키는 테스트는 없다. 결정이 먼저다 |
| `technique` | **필수** | 테스트 설계 템플릿 번호와 이름 (`templates/test-design/`), 또는 기법 이름 | 템플릿에 없는 기법이면 이름을 쓴다 |
| `checklist` | **필수** | 적용한 체크리스트 항목 `B-<n>`, `C-A<n>` | 해당 없으면 `none` |
| `decisions` | 값을 쓰는 모듈은 **필수** | 사람이 정한 값의 출처 `D-<번호> (<무엇>)` | 모듈 안의 모든 경계 · 범위 · 해상도 · 매개변수 범위가 여기 있는 D 중 하나에서 와야 한다 (C-A3) |
| `not-covered` | 선택 | 이 모듈이 의도적으로 검사하지 않는 것과 이유 | H3 승인 자료의 "잡지 않는 것"과 맞춘다 |

## 2. 테스트 함수 단위

| 규칙 | 예 |
|:---|:---|
| 각 테스트의 설명(docstring · 주석) 첫머리에 그 테스트가 지키는 ID를 적는다 (B-2) | `"""D-21: 경계 − 최소 해상도는 아래쪽 규칙이다."""` |
| 모듈 머리말의 `guards`에 없는 ID를 테스트에서 처음 인용하지 않는다 | 새 ID가 필요하면 머리말에 먼저 더한다 |
| 경계 행 · 표의 각 행 ID는 사람이 읽는 이름 | `ids=["B", "B-eps", "B+eps"]` |

## 3. 값의 출처 표시 (C-A3)

테스트 안의 값 중 **사람이 결정해야 하는 것**(정의역 경계, 해상도, 매개변수 범위, 경계 소속)은 상수로 모으고 같은 줄 또는 바로 위에 결정 ID를 적는다. 골격에서는 이 자리를 `[사람 결정 C-A3]` 표시와 `<D-xx: ...>` 자리표시자로 둔다.

```
# [사람 결정 C-A3] 정의역: 테스트 작성자가 추측하지 않는다. D-xx 에 없으면 H2 로 돌린다
MIN = <D-xx: 최소>
MAX = <D-xx: 최대, 상한이 없으면 None>
```

채운 뒤에는 `# D-21` 같은 결정 ID만 남긴다. `[사람 결정` 표시가 남아 있으면 아직 결정되지 않은 것이다.

## 4. 기계 검사: 게이트 GT (`harness/traceability.py`)

게이트 GT(`harness/traceability.py`)가 이 규약을 기계적으로 검사한다. 설정(`config/gates.toml` 의 `[gate]` kind = "traceability")에서 검사 항목(`checks`)을 지정할 수 있다.

| 검사 이름 | 검사 대상 및 방법 | 실패 시 메시지 머리 |
|:---|:---|:---|
| `header` | 모든 테스트 모듈의 첫 문서 블록에 `guards:` · `technique:` · `checklist:` 줄 존재 확인 | `[머리말]` |
| `id_format` | `guards`의 각 항목이 `^(FR-\d{3}|INV-\d+|D-\d+)$` 형식인지 검사. 열린 질문(`O-`) 인용 금지 | `[ID]` |
| `undecided` | 잠금 대상 테스트에 미결정 표시(`[사람 결정` 기본값)가 0건인지 확인 | `[미결정]` |
| `forward` | 명세의 모든 FR이 어느 모듈의 `guards`에 있는지 검사 (슬라이스 범위 밖 또는 `deferred` 제외) | `[정방향]` |
| `backward` | `guards`에 인용된 모든 FR · INV · D가 명세 및 결정 기록에 실제로 존재하는지 역방향 검사 | `[역방향]` |
| `assumptions` | 명세 가정(`## Assumptions`) 항목마다 결정(`D-##`) 또는 사람 구간(`H#`) 승격 표기 확인 | `[가정]` |
| `clarifications` | 명세 명확화(`## Clarifications`) 답변마다 결정(`D-##`) 또는 사람 구간(`H#`) 승격 표기 확인 | `[명확화]` |
| `needs_clarification` | 명세 본문에 미결정 표시(`[NEEDS CLARIFICATION`)가 남아 있지 않은지 확인 | `[명확화 필요]` |
| (항상) | 같은 FR · INV · D 가 정의 줄로 두 번 이상 나오지 않는지 | `[중복 정의]` |

정의 · 승격으로 인정하는 형식(목록 첫 낱말 · 표 첫 칸 · `→ D-##`)과 검사 밖 영역(HTML 주석 · 코드 블록)은 `docs/sdd-integration.md` "GT 가 명세를 읽는 규칙".
검사 로직은 하네스(Core), 요구 목록과 ID는 프로젝트에 둔다. 다른 언어 어댑터도 같은 키를 그 언어의 파일 머리 주석에 쓴다. 전체 게이트에서는 미룬 요구(`deferred`)가 없어야 통과한다(HD-07).
