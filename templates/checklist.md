# H3 테스트 승인 체크리스트

## 언제 쓰나

H3에서 테스트를 잠그기 **전에** 쓴다. 테스트 작성자는 H3 승인 자료를 만들 때 이 질문으로 스스로 점검하고, 사람은 승인할 때 같은 질문으로 확인한다. 기본 질문(§1)은 모든 슬라이스에, 추가 항목(§2 C-A)은 적용 범위에 맞는 슬라이스에 적용한다. H3 승인 자료의 머리말에 이 문서를 링크하고 적용한 항목 ID를 적는다. 체크리스트는 판단을 대신하지 않고, 빠뜨리기 쉬운 질문을 상기시킨다.

## 1. 기본 질문 (모든 슬라이스)

- [ ] **B-1 가장 게으른 구현 질문:** 이 테스트를 통과하는 가장 게으른 구현은 무엇인가? 그 구현이 틀렸다면 테스트가 부족하다.
  - 빈 목록을 돌려주는 구현이 통과하는가? (완전성 검사가 있는가)
  - 아무것도 하지 않거나 기록하지 않는 구현이 통과하는가? (공허한 참 방지가 있는가)
  - 예시 값만 하드코딩한 구현이 통과하는가? (성질 테스트 · 독립 오라클이 있는가)
- [ ] **B-2** 각 테스트가 지키는 불변식 · 결정 · 요구 ID가 테스트 설명에 적혀 있는가?
- [ ] **B-3** 경계값 표에 경계 **양쪽**(정확히 경계, 경계 − 최소 해상도)이 다 있는가?
- [ ] **B-4** 금지된 동작에 대해 "예외가 난다"뿐 아니라 **"상태가 바뀌지 않았다"**도 검사하는가?
- [ ] **B-5** 부수효과를 **횟수**로 검사하는가?
- [ ] **B-6** 오라클이 검사 대상 코드를 재사용하지 않는가? (재사용하면 같은 버그를 공유한다)
- [ ] **B-7** 환경이 없을 때 테스트가 조용히 skip하지 않고 **실패**하는가?
- [ ] **B-8** 테스트 이름만 읽어도 명세가 이해되는가?
- [ ] **B-9** 게으른 구현 검사 표에 **정상 빌드 행**이 있고 통과하는가? 검증 빌드가 실제로 import되었는가?

## 2. 추가 항목 (C-A)

### 적용 규칙

| 규칙 | 내용 |
|:---|:---|
| 상태 | `가설` → `회고 N건` (기존 테스트에 적용해 실제 약점을 찾음) → `사전 N건` (H3에서 적용한 뒤 레드팀이 같은 유형으로 뚫지 못함) |
| 상태가 낮아도 적용 | 적용해 봐야 검증된다 |
| 폐기 | 사전 검증에서 같은 유형의 우회가 통과하면 그 항목은 폐기하거나 다시 쓴다. 폐기한 항목도 지우지 않고 표시한다 |
| 기본 질문으로 승격 | `사전 1건` 이상인 항목만 |
| 상태 칸 | 아래 상태는 **참조 프로젝트의 검증 결과**다. 프로젝트는 §7에 자기 검증 이력을 쌓고 상태를 갱신한다 |

| ID | 질문 | 막는 실패 (일반) | 적용 범위 | 테스트 설계 | 상태 |
|:---|:---|:---|:---|:---|:---|
| **C-A1** | 성질 테스트의 입력 범위가 **명세의 정의역 전체**를 덮는가? 명세에 상한이 없으면 큰 값도 뽑는가? | 테스트가 뽑지 않는 큰 값에서 결과를 자르는 구현이 통과 | 숫자 · 시간 · 크기를 입력으로 받는 순수 로직 | 02, 06 | 회고 2건 |
| **C-A2** | 경계값 표에 **경계 ± 최소 해상도** 행이 있는가? 성질 테스트가 경계 근처를 따로 뽑는가? | 입력을 거친 단위로 반올림 · 절삭하거나 경계에 허용 오차를 둔 구현이 통과 | 경계 규칙이 있는 계산 | 01, 03 | 회고 3건 |

## 3. 층의 구분: 이 체크리스트에는 값이 들어가지 않는다

| 층 | 들어가는 것 | 서비스가 바뀌면 |
|:---|:---|:---|
| **하네스** (이 문서, 게이트, 실행기) | 값이 갖춰야 할 **형식**과 그것을 검사하는 규칙 | 그대로 |
| **프로젝트 명세** (결정 기록의 D-xx) | 실제 **값** (단위, 최소, 최대, 정밀도) | 서비스마다 다름 |

**규칙:** 체크리스트 항목에 특정 숫자 · 단위 · 도메인 용어가 들어가면 그 항목은 프로젝트 명세로 옮긴다.

## 4. 설계 원칙 후보 (하네스 층)

체크리스트 항목은 아니지만 도메인과 무관하게 나온 원칙이다. H3과 포트 설계(H4)에서 함께 본다.

| ID | 원칙 | 상태 |
|:---|:---|:---|
| **DP-1** | 도메인 안에서는 입력의 정밀도를 자르거나 반올림하지 않는다. 정규화는 시스템 경계(어댑터)에서만, 명시적으로 한다 | 가설 (참조 프로젝트 회고 근거 있음) |

## 5. 기계화 후보 (구현하지 않음)

프로젝트가 정의역을 기계가 읽을 수 있는 파일로 선언하면(이름 · 단위 · 최소 · 최대), 하네스가 도메인과 무관하게 다음을 검사할 수 있다. 검사 로직은 하네스, 선언 파일은 프로젝트에 둔다. **사전 검증 2건 이상**인 항목만 기계화한다.

- 성질 테스트의 입력 범위가 선언된 정의역을 덮는가 (C-A1)
- 공개 함수의 매개변수 중 선언되지 않은 것이 있는가 (C-A3)

## 6. 이 체크리스트가 다루지 않는 것

- 부수효과가 있는 도메인(외부 결제 멱등성, 동시 쓰기, 개인정보 로그)에서 나온 항목은 아직 없다. 해당 도메인은 레드팀을 한 바퀴 거쳐 자기 항목을 얻기 전까지 "검증된 항목 없음"으로 본다.
- 하네스 장치(보호 경로, 구조 규칙)가 막는 우회는 여기 적지 않는다. 장치의 수정 이력은 문제 기록에 있다.

## 7. 검증 이력 (프로젝트가 채움)

| 일자 | 종류 (회고 / 사전) | 대상 | 결과 |
|:---|:---|:---|:---|
| <YYYY-MM-DD> | <회고> | `<테스트 파일>` | <항목별로 찾은 약점, 실행 확인 여부> |

**한계를 함께 적는다:** 회고 대상이 같은 작성자 · 같은 종류의 로직이면, 결과는 그 범위까지의 일반화만 보여 준다.
