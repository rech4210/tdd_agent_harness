# 10 게으른 구현 검증 절차

| 항목 | 내용 |
|:---|:---|
| 체크리스트 | B-1, B-9, C-A1 ~ C-A7 (후보의 출처) |
| 쓰는 곳 | H3 승인 자료 §2, 회귀 세트(방어 유지), 체크리스트 회고 |

## 목적

"이 테스트가 그 게으른 구현을 막는다"는 주장을 **실행으로** 확인한다. 검증용 빌드에서 후보를 하나씩 켜고 끄며, 정상 빌드는 통과하고 모든 후보는 실패하는지 본다. 이 절차는 테스트가 아니라 **테스트를 검사하는 장치**다. 그래서 장치 자체의 공허한 참을 먼저 막아야 한다.

## 언제 쓰나

| 시점 | 목적 |
|:---|:---|
| H3 승인 전 | 보강한 테스트가 노린 후보를 실제로 잡는지 |
| 하네스 · 테스트 변경 후 | 이전에 잡던 후보를 여전히 잡는지 (회귀) |
| 체크리스트 회고 | 기존 테스트에 C-A 항목을 적용해 찾은 약점이 진짜인지 (후보가 기존 테스트를 통과하고 명세를 어기는지) |

## 무엇을 막나

| 실패 | 일반화된 사례 |
|:---|:---|
| 막는다고 믿은 테스트가 실제로는 통과시킴 | 표적 생성기가 없을 때 한 후보가 보강한 테스트를 통과했다. 실행 확인에서 드러나 표적 테스트를 더했다 |
| **검증 장치의 공허한 참** | 회귀 스크립트를 처음 돌렸을 때 **모든 후보가 통과**로 나왔다. 테스트 실행기의 설정 파일에 있는 import 경로가 환경 변수보다 앞서서, 검증 빌드 대신 저장소의 실제 구현이 import되었기 때문이다 |
| 잘못된 이유의 실패 | 후보가 import 오류 · 수집 오류로 실패하면 "잡혔다"처럼 보이지만 아무것도 검사하지 않았다 |
| 끝나지 않는 후보 | 검증 누락으로 무한 루프에 빠진 후보가 판정을 멈춘다 |

## 기본 후보 (모든 슬라이스, 필수 — 체크리스트 B-10)

슬라이스마다 아래 두 유형을 후보 목록에 먼저 넣고 시작한다. 반복해서 나온 빈틈을 매번 검토자가 다시 찾게 하지 않기 위해서다(시험 저장소 1단계: 검토 지적 6회 중 5회가 이 두 유형, 자동 승인 조건 `--base-types unbounded,reject-preserve`).

| 유형 | 후보 예 | 테스트가 잡아야 하는 것 |
|:---|:---|:---|
| 상한 없는 표적 (`unbounded`) | 상한 없는 값을 고정 폭 정수 · 부동소수로 바꾸는 구현, 큰 개수에서 잘라 버리는 구현, 넘침 예외를 삼키는 구현 | 아주 큰 값(10^100, 지수 표기 극단, 매우 많은 항목)에서도 정확한 결과 또는 명세가 정한 거부 |
| 거부 경로 입력 보존 (`reject-preserve`) | 거부하기 전에 입력 목록 · 상태를 먼저 바꾸는 구현, 거부할 때 부분 결과를 남기는 구현 | 모든 거부 경로마다 “결과 없음 + 입력 · 상태 그대로” |

## 절차

| 단계 | 할 일 | 확인 |
|:---|:---|:---|
| 1. 검증 빌드 분리 | 제품 경로 **밖**에 검증용 정상 구현을 둔다 (저장소 밖 임시 복제본, 또는 판정 범위 밖의 회귀 디렉터리). 제품 아님 · 병합 대상 아님 · 구현자에게 주지 않음 | 제품 경로에 후보 스위치 문자열이 0건 |
| 2. 후보 목록 | 후보마다 ID, 한 줄 설명, 출처 항목(C-Axx), **명세를 어기는 입력** | 명세 위반 입력이 없으면 후보가 아니다 (동작으로 구별 불가 → "잡지 않는 것") |
| 3. 후보 스위치 | 환경 변수 `LAZY=<후보 ID>`일 때만 게으른 분기. 비어 있으면 정상 | 스위치가 꺼졌을 때 분기가 없는 것과 같다 |
| 4. import 경로 고정 | 실행기 설정의 경로가 환경 변수보다 앞설 수 있다. **실행기 설정을 명령줄에서 덮어쓴다** | **매 실행마다** import된 모듈 경로를 출력하고 검증 빌드인지 확인 |
| 5. 결정적 실행 | 무작위 seed 고정, 테스트 시간 제한, 게이트와 같은 환경 변수 | 같은 입력에서 같은 결과 |
| 6. 실행표 | **정상 빌드 행**(통과해야 함) + 후보 행(실패해야 함) | 정상 빌드 행이 없거나 실패하면 표 전체가 무효 |
| 7. 실패의 종류 | 후보의 실패는 **테스트 실패**여야 한다 (시간 초과 포함). 수집 오류 · 사용 오류 · 테스트 0개는 불일치 | 실행기의 종료 코드로 구분 |
| 8. 판정 | 정상 통과 ∧ 모든 후보 실패 ∧ 모든 행이 검증 빌드를 import → 종료 코드 0. 하나라도 어긋나면 1 | |
| 9. 후보가 통과하면 | 명세 위반 입력 재확인 → 테스트 보강(03 표적 등) → H3 자료 갱신 → 재실행. 구별 불가면 "잡지 않는 것"에 적고 누가 대신 보는지 적는다 | |

### 후보 유도표

| 출처 | 후보의 형태 |
|:---|:---|
| C-A1 | 큰 입력에서 값을 자르거나 상한을 둠 |
| C-A2 | 경계에 허용 오차, 거친 단위로 반올림한 뒤 비교 |
| C-A3 | 생성 · 비교 시 정밀도 절삭 |
| C-A4 | 값 객체의 비교가 항상 참 |
| C-A5 | 매개변수가 테스트 값이 아니면 빈 결과, 목록 길이 상한 |
| C-A6 | 거부 조건 일부만 검사, 한 인자만 검사, 하위 필드 검증 누락 |
| C-A7 | 받은 값을 저장하지 않음 |
| B-4 | 금지 전이에서 상태를 먼저 바꿈 |
| B-1 | 빈 목록 반환, 아무것도 하지 않음 |
| 시간 제한 | 검증 누락으로 끝나지 않는 계산 |

### 결과 표 (H3 승인 자료 §2에 붙인다)

| 구현 | import 대상 | 결과 |
|:---|:---|:---|
| 정상 | `<검증 빌드 경로>` | 통과 (<N>건) |
| <후보 ID> | `<검증 빌드 경로>` | **실패** (<실패 테스트 수>) |

## 최소 구조

```
CASES = [ ("", 테스트), (후보1, 테스트), (후보2, 테스트), ... ]   # 첫 행은 정상 빌드
for (후보, 테스트) in CASES:
    env = { LAZY: 후보, 검증 빌드 경로를 import 경로로 }
    결과 = 테스트 실행기(테스트, seed 고정, 시간 제한, 실행기 설정의 import 경로를 명령줄에서 덮어씀)
    import 대상 = 결과에서 읽은 실제 import 경로
    기대 = (후보 == "") ? 통과 : 테스트 실패
    일치 = (결과 == 기대) ∧ (import 대상 ⊂ 검증 빌드)
종료 코드 = 모든 행 일치 ? 0 : 1
```

## 게으른 구현 예 (검증 장치 쪽)

| 게으른 장치 | 왜 틀리나 | 이 절차의 대응 |
|:---|:---|:---|
| 실제 구현을 import한 채 실행 | 모든 후보가 통과로 보인다 (또는 모든 행이 같은 결과) | 단계 4: 행마다 import 대상 확인 |
| 정상 빌드 행 없이 후보만 실행 | 검증 빌드 자체가 틀려서 모든 후보가 실패해도 "잡힘"으로 보인다 | 단계 6: 정상 빌드 행 필수 |
| 0이 아닌 종료 코드를 모두 "실패"로 셈 | import 오류 · 테스트 0개가 "잡힘"이 된다 | 단계 7: 테스트 실패만 인정 |
| seed 비고정 | 후보가 가끔 통과한다 | 단계 5 |

## 흔한 실수

| 실수 | 결과 |
|:---|:---|
| 후보 스위치를 제품 코드에 넣음 | 병합되면 그 자체가 우회 경로다. 검증 빌드는 제품 경로 밖에 |
| import 대상을 한 번만 확인 | 실행 방식이 다른 행에서 다른 모듈이 import될 수 있다. 매 행 확인 |
| 무한 루프 후보에 시간 제한 없음 | 판정이 멈춘다 |
| import 확인을 실행 끝에서만 출력 | 시간 제한이 프로세스를 바로 끝내는 방식이면 확인이 사라져, 시간 초과로 잡힌 후보가 불일치로 보인다. 수집 직후에 파일로 기록한다 |
| 통과한 후보를 바로 "테스트 결함"으로 판정 | 먼저 그 후보가 명세를 실제로 어기는 입력을 확인한다 |
| 검증 빌드를 구현자에게 줌 | 정답을 준 것이다. 구현자의 정보 조건이 오염된다 |

## Python 참조 구현

검증 빌드의 후보 스위치 (제품 경로 밖, 예: `regression/lazy_build/src/mypkg/calc.py`):

```python
import os

LAZY = os.environ.get("LAZY", "")  # 비어 있으면 정상 빌드


def price_for(q: int) -> int:
    if LAZY == "X-A1" and q > 1_000_000:  # 후보: 큰 입력에서 자름 (C-A1)
        q = 1_000_000
    return q * 10
```

import 확인 플러그인 (`regression/import_probe.py`). 수집 직후 파일에 기록한다. 시간 제한 플러그인이 스레드 방식(Windows 기본)으로 프로세스를 바로 끝내면 끝에서 출력하는 확인은 사라지기 때문이다:

```python
import os
import sys
from pathlib import Path


def _record():
    mod = sys.modules.get(os.environ["PROBE_PACKAGE"])
    Path(os.environ["PROBE_OUT"]).write_text(str(getattr(mod, "__file__", None)), encoding="utf-8")


def pytest_collection_finish(session):
    _record()


def pytest_terminal_summary(terminalreporter):
    _record()  # 테스트 안에서 늦게 import 한 경우
```

실행기의 핵심 (전체 골격: `templates/test-skeletons/lazy_candidates_skeleton/run_lazy_candidates.py`):

```python
# 행 하나의 실행. BUILD = 검증 빌드 경로, probe_out = 저장소 밖 임시 파일
env = {**os.environ, "LAZY": lazy, "PROBE_PACKAGE": PACKAGE, "PROBE_OUT": str(probe_out),
       "PYTHONPATH": os.pathsep.join([str(BUILD), str(PROBE_DIR)])}
p = subprocess.run(
    [sys.executable, "-m", "pytest", "-q", "-p", "no:cacheprovider", "-p", "import_probe", test,
     "--hypothesis-seed=0", "--timeout=60",
     # 설정 파일의 pythonpath 가 PYTHONPATH 보다 앞서 실제 구현을 import 한다. 명령줄에서 덮어쓴다.
     # 검증 빌드를 맨 앞에, '.' 은 tests 패키지 import 용
     "-o", f"pythonpath={BUILD.as_posix()} ."],
    cwd=ROOT, env=env, capture_output=True, text=True,
)
imported = probe_out.read_text(encoding="utf-8")
from_build = imported != "None" and Path(imported).resolve().is_relative_to(BUILD.resolve())
expected = 0 if lazy == "" else 1  # 1 = 테스트 실패 (시간 초과 포함). 2 · 3 · 4 · 5 는 잡힌 것이 아니다
good = p.returncode == expected and from_build
```

실행 확인 (참조용 작은 프로젝트, 설정 파일에 `pythonpath = [".", "src"]`): 덮어쓰기가 있으면 정상 통과 · 후보 3개(자르기 · 매개변수 고정 · 시간 초과) 모두 실패 · 모든 행이 검증 빌드를 import했다. 덮어쓰기를 빼면 모든 행이 저장소의 실제 구현을 import했고 **모든 후보가 통과**했다.
